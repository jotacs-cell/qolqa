Convenciones generales

Reglas que aplican a todos los endpoints de abajo, para no repetirlas en cada uno.

Todo endpoint que no sea /api/auth/login exige el header Authorization: Bearer <token>. Sin token válido: 401. Con token válido pero rol insuficiente: 403.

Formato estándar de error

{
  "error": {
    "codigo": "STOCK_INSUFICIENTE",
    "mensaje": "No hay stock suficiente para el producto solicitado.",
    "detalle": { "producto_id": 42, "stock_disponible": 3 }
  }
}

Paginación (listados)

Query params: page (default 1), limit (default 20, máx 100). Respuesta:

{
  "data": [ /* ... */ ],
  "paginacion": { "page": 1, "limit": 20, "total": 134, "total_paginas": 7 }
}

01 Autenticación y accesos

Login con JWT y control de acceso por rol. Los tres roles del sistema son admin, supervisor y cajero.

RolPuede
cajeroOperar el POS (registrar ventas), consultar productos, ver su propio historial de ventas.
supervisorTodo lo del cajero, además gestionar el catálogo de productos y anular ventas.
adminTodo lo del supervisor, además gestionar usuarios y ver reportes globales.

CRUD del catálogo. La eliminación es siempre lógica: un producto con ventas asociadas nunca se borra de la base de datos, solo cambia su estado.

03 Motor de ventas (POS)

El endpoint central del sistema. Recibe el carrito armado en el frontend y ejecuta la transacción completa en una sola operación atómica.

POST /api/ventas Registra una venta completa (cabecera + detalle + descuento de stock)

Request body

{
  "cliente_id": null,
  "metodo_pago": "tarjeta",
  "items": [
    { "producto_id": 101, "cantidad": 2 },
    { "producto_id": 87,  "cantidad": 1 }
  ]
}
El precio nunca lo manda el frontend. El backend busca precio_venta de cada producto al momento de procesar y lo congela en precio_unitario_historico. Así se evita que un carrito manipulado en el cliente altere el total.

Qué hace el controlador, dentro de una única transacción SQL

BEGIN;
  1. Por cada item: SELECT precio_venta, stock FROM productos
     WHERE id = ... FOR UPDATE;   -- bloquea la fila
  2. Si algún stock es insuficiente → ROLLBACK, responde 409.
  3. INSERT INTO ventas (cabecera) ... RETURNING id;
  4. INSERT masivo en detalle_ventas con precio_unitario_historico
     tomado en el paso 1.
  5. UPDATE productos SET stock = stock - cantidad ...
     (el CHECK stock >= 0 es la última red de seguridad).
COMMIT;

Respuesta 201

{
  "id": 5820, "fecha": "2026-08-27T15:12:03Z",
  "total": 10.50, "metodo_pago": "tarjeta",
  "estado_documento": "emitida",
  "items": [
    { "producto_id": 101, "cantidad": 2, "precio_unitario_historico": 3.50, "subtotal": 7.00 },
    { "producto_id": 87,  "cantidad": 1, "precio_unitario_historico": 3.50, "subtotal": 3.50 }
  ]
}
409Stock insuficiente en uno o más productos — no se registra nada, rollback automático.
422Carrito vacío, cantidad ≤ 0, o producto inexistente/inactivo.
GET /api/ventas Listado con filtros — base del dashboard

Query params

?desde=2026-08-01&hasta=2026-08-27
&usuario_id=7          // un cajero solo ve las suyas
&estado_documento=emitida
&page=1&limit=20
Un usuario con rol cajero solo puede consultar sus propias ventas; el filtro usuario_id queda forzado por el backend a su propio id, sin importar lo que mande el query string.
GET /api/ventas/:id Detalle completo de una venta, con sus líneas
404No existe, o pertenece a otro cajero sin permiso para verla.
PATCH /api/ventas/:id/anular supervisor+ Anula una venta emitida y repone el stock descontado

Request body

{ "motivo": "error de cobro" }
Nunca se hace DELETE sobre ventas: el registro es historial contable. Solo funciona mientras el comprobante todavía no fue aceptado por SUNAT (pendiente, en error o rechazado). Si ya fue aceptado, usa PATCH /api/comprobantes/:id/anular en su lugar.
409La venta ya estaba anulada.
409El comprobante ya fue aceptado por SUNAT — hay que anular con nota de crédito, no aquí.

04 Notas de crédito y anulación

Único mecanismo legal para modificar o cancelar una factura/boleta que SUNAT ya aceptó — nunca se edita ni se borra un comprobante aceptado.

CódigoMotivo (catálogo 09 SUNAT)Repone stock
01Anulación de la operaciónSí
02Anulación por error en el RUCNo
03Corrección por error en la descripciónNo
04 / 05Descuento global / por ítemNo
06Devolución totalSí
07Devolución por ítemSí
08BonificaciónNo
09–12Otros ajustes de valor / exportación / IVAPNo
POST /api/comprobantes/:id/notas-credito supervisor+ Emite una nota de crédito (total o parcial) sobre un comprobante aceptado

Request body — devolución parcial

{
  "codigo_motivo": "07",
  "motivo_detalle": "Cliente devolvió 1 unidad en mal estado",
  "items": [
    { "producto_id": 101, "cantidad": 1 }
  ]
}
items es opcional: si se omite, la nota cubre todas las líneas del comprobante (equivalente a una anulación/devolución total). El backend nunca deja acreditar más unidades de las que quedan disponibles, aunque se emitan varias notas parciales sobre el mismo comprobante.

Respuesta 201

{ "id": 812, "estado": "aceptado", "codigo": "0", "descripcion": "La Nota de Crédito ha sido aceptada" }
409El comprobante afectado aún no fue aceptado por SUNAT.
409Ya fue acreditado en su totalidad (por esta u otra nota anterior).
422codigo_motivo fuera del catálogo 09, o cantidad mayor al saldo disponible.
PATCH /api/comprobantes/:id/anular supervisor+ Cancela por completo una factura o boleta ya aceptada

Request body

{ "motivo": "Venta duplicada por error del cajero" }
Atajo sobre POST /notas-credito con codigo_motivo: "01" cubriendo el 100% de las líneas. Repone todo el stock y, en la misma operación, marca la venta original como anulada — el equivalente a "anular esta factura" en el mostrador.

Respuesta 201

{ "notaCreditoId": 813, "ventaAnulada": true, "estado": "aceptado" }
GET /api/comprobantes/:id/notas-credito Lista las notas de crédito emitidas sobre un comprobante
GET /api/comprobantes/:id/pdf Representación impresa (boleta, factura o nota de crédito) en PDF
Es lo que se le entrega al cliente en el mostrador o se le envía por correo. Incluye el código QR que exige SUNAT para la representación impresa (RUC, tipo, serie-correlativo, IGV, total, fecha y hash). No tiene valor legal por sí solo — eso lo tiene el XML firmado + su CDR, disponibles en /xml y /cdr.

05 Dashboard y analítica

Datos de gestión — todos exigen rol supervisor o admin; un cajero no puede consultarlos. Todos aceptan ?desde=YYYY-MM-DD&hasta=YYYY-MM-DD (por defecto, los últimos 30 días) excepto el resumen de hoy.

GET /api/dashboard/resumen-hoy Recaudación de hoy, N° de ventas, ticket promedio y variación vs. ayer 
{
  "recaudacion_hoy": 1284.50, "ventas_hoy": 47,
  "ticket_promedio": 27.33, "variacion_vs_ayer_pct": 12.4
}
GET /api/dashboard/recaudacion-diaria Serie de tiempo: recaudación y N° de ventas por día — para graficar
GET /api/dashboard/productos-top Productos de mayor rotación por unidades vendidas (?limit=, por defecto 10)
GET /api/dashboard/rendimiento-vendedores Monto vendido, N° de ventas y ticket promedio por cajero/vendedor

Códigos de estado HTTP usados en la API

CódigoSignificado en este sistema
200Consulta u operación exitosa (GET, PATCH, PUT).
201Recurso creado (usuario, producto o venta nuevos).
400Body malformado (JSON inválido, falta un campo requerido).
401Token ausente, expirado o inválido.
403Token válido, pero el rol no tiene permiso para esta acción.
404El recurso solicitado no existe.
409Conflicto de estado: stock insuficiente, código de barras duplicado, venta ya anulada.
422Datos válidos en formato pero inválidos en reglas de negocio (precio negativo, cantidad ≤ 0).
500Error no controlado del servidor — se registra en logs, nunca expone detalles internos al cliente.
