01Enfoque y nombre provisional

Un nombre de trabajo, para no seguir escribiendo "[NOMBRE DEL SISTEMA]" en cada documento — cámbialo cuando quieras, es un placeholder hasta que verifiques disponibilidad de marca y dominio.

Qolqa ERP — qolqa, del quechua, nombraba el depósito donde el imperio inca almacenaba y ordenaba sus recursos: el sistema hace lo mismo con la información de un negocio. Es corto, no colisiona con marcas de facturación existentes, y funciona bien como qolqa.pe.

Alternativas si prefieres otro registro: Yachay (quechua, "conocimiento") o Illari (quechua, "amanecer"). Cualquiera de los tres es un placeholder de trabajo — antes de invertir en marca, verifica en INDECOPI que el nombre elegido esté libre.

Cómo leo el encargo

Es una plataforma con dos productos entrelazados pero distintos: un negocio SaaS (planes, suscripciones, cobro recurrente, panel de super admin) que empaqueta un ERP (ventas, compras, inventario, finanzas) cuyo primer módulo funcional es facturación electrónica SUNAT. Ya construimos y probamos el motor de facturación electrónica (ventas, comprobantes, NubeFacT, PDF con estado SUNAT, roles y auditoría) para un negocio de una sola empresa en este mismo proyecto — es la base real de la Fase 3 de este roadmap, no un punto de partida en cero: hay que generalizarlo a multiempresa (agregar company_id, credenciales por empresa) más que reescribirlo.

03Arquitectura general

Dos caminos desde la API: el síncrono, que responde en el momento (CRUD, consultas), y el asíncrono por colas, para todo lo que depende de un tercero o toma tiempo.

04Arquitectura multi-tenant

La condición no negociable del encargo: "no permitir bajo ninguna circunstancia que un usuario pueda consultar, modificar o eliminar información de otro tenant." Eso no se logra con una sola capa — se logra con varias, cada una asumiendo que la anterior puede fallar.

Estrategia elegida: base compartida + company_id + Row-Level Security

Con la meta de escalar de 100 a 100,000 empresas (punto 34), una base de datos por empresa es inviable operativamente (migraciones, backups y conexiones se multiplican por cada tenant). Se usa una única base compartida, con cada tabla de negocio llevando company_id, reforzada con políticas de PostgreSQL a nivel de motor — no solo a nivel de aplicación.

Una decisión de diseño que aclaro aquí

El encargo usa tenant_id como ejemplo, pero también pide multiempresa por usuario (punto 27) y multisucursal (punto 28). Separo dos conceptos: tenants es la cuenta que paga la suscripción, y companies es cada RUC que opera bajo esa cuenta (el Plan Empresa permite más de una). El aislamiento real de datos comerciales — ventas, clientes, stock — es por company_id, no por tenant_id: dos empresas con RUC distinto bajo la misma suscripción tampoco deben verse los datos entre sí.

Las cinco capas de aislamiento

  1. Origen del dato: el company_id sale únicamente del JWT firmado en el login — nunca de un header, query param o campo del body que el cliente pueda enviar.
  2. Middleware de aplicación: TenantMiddleware resuelve la empresa activa y la guarda en AsyncLocalStorage para toda la duración de la petición.
  3. Repositorio base: una extensión de Prisma inyecta WHERE company_id = :actual en cada consulta de una tabla de negocio — no es una convención que un desarrollador pueda olvidar, es estructural.
  4. Row-Level Security de PostgreSQL: cada tabla de negocio tiene una política USING (company_id = current_setting('app.company_id')::uuid), y cada transacción abre con SET LOCAL app.company_id. Es la red de seguridad real: funciona incluso si el paso 3 tuviera un error.
  5. Pruebas dedicadas: una suite que, autenticada como la Empresa A, intenta leer o escribir un registro de la Empresa B y espera que falle — se ejecuta en cada build, no es una prueba manual ocasional.

El Super Admin es la única excepción intencional: opera con un rol de base de datos separado que sí puede saltar RLS, usado exclusivamente por endpoints bajo platform.* y siempre registrado en auditoría — no hay ninguna ruta de una empresa normal que pueda alcanzar ese privilegio.

Para el Plan Empresa, si algún cliente grande exige aislamiento físico adicional por motivos de cumplimiento, el mismo esquema admite pasar esa cuenta puntual a base de datos propia sin rediseñar el sistema — se deja anotado como camino futuro, no construido en la Fase 1.

06Estructura de carpetas

Monorepo con pnpm workspaces. Cada módulo de negocio es autocontenido en el backend (controller → service → repository), y el frontend refleja el mismo mapa de módulos que el menú de la sección 07.

apps/ api/ # NestJS src/modules/ auth/ tenants/ billing/ users/ rbac/ customers/ suppliers/ catalog/ inventory/ sales/ purchases/ finance/ electronic-billing/ providers/ electronic-billing-provider.interface.ts nubefact.provider.ts sunat-direct.provider.ts # futuro, no en Fase 1-3 electronic-billing.service.ts reports/ notifications/ audit/ super-admin/ src/common/ # guards, interceptors, decoradores, filtros src/database/ # schema Prisma, migraciones, seeders web/ # React SPA src/modules/ # ventas, compras, inventario, finanzas, facturación… src/components/ src/hooks/ src/lib/ workers/ # procesos BullMQ: facturación, correo, recordatorios packages/ shared-types/ # DTOs y esquemas Zod compartidos api ↔ web ↔ workers infra/ docker-compose.yml migrations/

El paquete shared-types es el detalle que evita el requisito 38 de "no duplicar código": el mismo esquema Zod que valida un formulario de factura en el navegador valida el DTO en el backend — una sola definición de "qué es una factura válida".

08Roles y permisos

Permisos granulares por acción, no por módulo entero — el mismo enfoque ya probado en el prototipo, ahora escalado a roles personalizados por empresa.

  • Cada permiso es una clave módulo.recurso.acción (ej. sales.invoice.void, inventory.stock.adjust, config.users.manage).
  • Los roles son paquetes de permisos. Los 5 roles base (ver tabla) se cargan como datos semilla, no como if en el código — cualquier empresa puede clonarlos y ajustarlos, o crear roles propios.
  • company_users asigna usuario + empresa + rol (+ sucursal opcional) — el mismo Juan puede ser Administrador en la Empresa A y Vendedor en la Empresa B.
  • El Super Admin vive en un espacio de permisos separado (platform.*), resuelto por un guard distinto — estructuralmente no hay forma de que un rol de empresa escale a permisos de plataforma.

09Planes y suscripciones

Todo lo que un plan limita vive en datos, en plans.límites (JSONB), para que el Super Admin cree o edite planes sin desplegar código.

PlanUsuariosEmpresasMódulosPrueba
Básico11Facturación, clientes, productos, reportes básicos14 días
Profesionalhasta 51+ Ventas, compras, inventario, caja, CxC14 días
Empresasin límite fijomúltiples+ multisucursal, inventario avanzado, finanzas, APIconfigurable

Un PlanLimitsService se consulta antes de cualquier acción que cuente contra un límite (crear un usuario, sumar una empresa, emitir el comprobante número 501 del mes) — nunca falla en silencio: responde 402/403 con un mensaje claro de qué límite se alcanzó y qué plan lo resuelve. El conteo de uso actual se calcula bajo demanda para la Fase 2 (una consulta COUNT); un contador en Redis solo se justifica cuando el volumen lo exija.

2 · EmpresaCrea companies en estado borrador; valida formato y dígito verificador del RUC. La consulta pública de RUC en SUNAT existe pero tiene límites de uso — útil para autocompletar razón social, no para depender de ella en producción sin probarla antes.

11Flujo de emisión de un comprobante

Asíncrono desde el primer momento: la venta se confirma en la base de datos antes de tocar a un tercero, y el envío a SUNAT ocurre después, en cola — el mismo diseño ya probado en el prototipo, ahora generalizado.

La interfaz de integración se mantiene desacoplada del motor de ventas, para poder cambiar de proveedor por empresa sin tocar la lógica de negocio:

interface ElectronicBillingProvider {
  send(document: ElectronicDocumentPayload, credentials: ProviderCredentials): Promise<ElectronicBillingResult>;
  checkStatus(externalId: string, credentials: ProviderCredentials): Promise<ElectronicBillingResult>;
}

12Riesgos legales y técnicos

Los que importan de verdad para un SaaS multiempresa de facturación electrónica en Perú — con lo que se pudo verificar y lo que queda pendiente de confirmar antes de comprometerse comercialmente.

Cada empresa necesita su propio camino a SUNAT

La plataforma no puede compartir un único certificado o cuenta OSE para todas las empresas sin ser ella misma un OSE homologado. Verifiqué que NubeFacT sí ofrece un programa Reseller OSE pensado exactamente para esto — software que da de alta a muchas empresas cliente bajo un panel único: cuenta reseller por pago único, más una cuota mensual por empresa activa. Son las cifras publicadas en su sitio al momento de esta consulta; hay que confirmarlas directamente con NubeFacT antes de fijarlas en un modelo de precios propio.

Camino recomendado para la Fase 3

Empezar más simple y barato: cada empresa trae su propia cuenta NubeFacT (o de otro OSE) y solo pega su ruta/token en company_billing_credentials — es exactamente el patrón ya construido y probado en el prototipo, sin costo ni contrato adicional para la plataforma. El modelo Reseller se evalúa después, cuando el volumen de empresas lo justifique.

No custodiar certificados digitales propios

Conectar directo a SUNAT (sin OSE) exigiría guardar el certificado .pfx y las claves SOL de cada empresa — responsabilidad legal alta si se filtran. Recomiendo no implementar SunatDirectProvider en las fases 1 a 3; dejar solo la interfaz preparada.

Retención legal de XML y CDR

SUNAT exige conservar los comprobantes electrónicos por el plazo de prescripción tributaria. No asumo aquí el número exacto de años vigente — se debe confirmar con un asesor tributario o la normativa SUNAT actual antes de definir cualquier política de borrado automático.

Datos personales de clientes y proveedores

La Ley N.° 29733 de Protección de Datos Personales aplica a lo que cada empresa registra de sus clientes. La plataforma actúa como encargada del tratamiento; conviene una política de privacidad propia y dejar contractualmente claro que cada empresa-cliente responde por sus propios datos ante la ley.

Concurrencia de correlativos

Ya resuelto en el prototipo con bloqueo de fila por serie + sucursal + empresa — se reutiliza el mismo patrón, no hay riesgo nuevo aquí.

Fuentes consultadas: NubeFacT — Reseller, NubeFacT — Reseller OSE para proveedores.

13Qué debe ser configurable

Nada de esto vive como constante en el código — todo se lee de una tabla, editable desde un panel.

  • Límites de cada plan (usuarios, empresas, sucursales, documentos/mes, almacenamiento)
  • Módulos habilitados por plan
  • Series y correlativos por empresa/sucursal
  • Tasas de impuestos (IGV y futuros)
  • Métodos de pago, de venta y de suscripción
  • Roles y permisos personalizados por empresa
  • Monedas y tipo de cambio
  • Proveedor de facturación electrónica por empresa
  • Plantillas de PDF (A4 / ticket / A5) y membrete
  • Umbrales de notificación y días de prueba por plan
